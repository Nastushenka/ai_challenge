# Nastia Chat — веб-интерфейс для нескольких LLM

Сторонние библиотеки не нужны.

```bash
cd web-simple
cp .env.example .env
# Впишите ключ в LLM_API_KEY внутри .env
python3 server.py
```

Откройте в браузере: <http://127.0.0.1:8000>

В интерфейсе можно переключаться между тремя моделями:

- `DeepSeek V4 Pro` — текущая основная модель;
- `Gemma 3 4B` — небольшая модель `google/gemma-3-4b-it` через Hugging Face;
- `Qwen 3 8B` — средняя модель `Qwen/Qwen3-8B` через Hugging Face.

Выбранная модель применяется к обычному запросу и обоим режимам сравнения.
DeepSeek и Hugging Face используют отдельные ключи в локальном файле `.env`:

- `LLM_API_KEY` — API-ключ;
- `LLM_BASE_URL` — `https://api.deepseek.com`;
- `LLM_MODEL` — `deepseek-v4-pro`.
- `DEEPSEEK_CONTEXT_WINDOW` — используемый лимит контекста DeepSeek;
- `HF_TOKEN` — токен Hugging Face с правом вызова Inference Providers;
- `HF_BASE_URL` — `https://router.huggingface.co/v1`;
- `HF_GEMMA_MODEL` и `HF_QWEN_MODEL` — идентификаторы моделей Hugging Face.
- `GEMMA_CONTEXT_WINDOW` и `QWEN_CONTEXT_WINDOW` — лимиты контекста моделей.

Файл `.env` исключён из Git и не попадёт в репозиторий.

## Простой LLM-агент

Логика общения с языковой моделью вынесена в отдельную сущность `SimpleAgent`
в файле `agent.py`. Агент хранит конфигурацию выбранной модели, принимает запрос
пользователя, формирует HTTP-запрос к API, разбирает ответ и возвращает текст.
Метод `run()` дополнительно возвращает время выполнения, количество токенов и
оценку стоимости, а метод `ask()` предоставляет простой текстовый результат.

Веб-сервер отвечает только за получение данных из интерфейса, проверку полей и
передачу задачи агенту. Обычный чат и все режимы сравнения используют один и тот
же класс агента, поэтому вызов API и обработка ответа полностью инкапсулированы.

## Интерфейс и токены

Настройки собраны в три смысловые группы: режим запуска, формат и завершение,
ограничения и вариативность. На узком экране панель настроек переносится под
основную рабочую область.

До отправки рядом со счётчиком символов показывается приблизительное количество
токенов. После ответа приложение выводит фактические данные API: время запроса,
входные, выходные и суммарные токены, а также ориентировочную стоимость. Метрики
показываются для обычного чата, каждого варианта в режимах сравнения и отдельного
итогового анализа.

## Задание 8 — рост контекста и переполнение

Для каждого обычного хода агент формирует отдельный отчёт:

- токены текущего запроса;
- токены всей истории до нового запроса;
- токены служебной инструкции;
- фактические входные токены по данным API;
- фактические токены ответа модели;
- доля заполнения контекстного окна.

Разбиение входа на запрос, историю и инструкцию рассчитывается локально и является
приблизительным, потому что у разных моделей разные токенизаторы. После ответа
общий вход и выход заменяются точными значениями из поля `usage` API. Интерфейс
явно отличает приблизительные значения знаком `≈`.

Метрики каждого хода сохраняются в SQLite вместе с диалогом. Поэтому после
перезапуска видны накопленные API-токены, стоимость и рост входного контекста.
Стоимость одного нового запроса обычно растёт: агент повторно отправляет модели
всю предыдущую историю.

До обращения к API агент сравнивает расчётный размер входа с контекстным окном
выбранной модели. При превышении вызов блокируется, история не изменяется, а сервер
возвращает HTTP 413 и подробный отчёт. Это показывает основное последствие
переполнения: модель не получает запрос и не может сформировать ответ. При
заполнении от 80% интерфейс заранее показывает предупреждение.

Под интерфейсом подготовлены три тестовых сценария: короткий диалог, длинный
диалог из 30 обменов и контекст, намеренно превышающий лимит. Они пересчитываются
при переключении модели и показывают ожидаемое поведение без дорогого запуска
огромного запроса. Автотесты дополнительно проверяют рост входных токенов и
стоимости, сохранение метрик после перезапуска и блокировку API при переполнении.

## Постоянная история диалога

Обычный чат сохраняется агентом в локальную SQLite-базу `conversation_history.db`.
Каждый диалог имеет отдельный идентификатор, который браузер сохраняет на устройстве.
При новом запросе агент загружает всю историю выбранного диалога и передаёт её
модели вместе с новым сообщением. Ограничения по количеству сохранённых реплик нет.
Поэтому контекст сохраняется после остановки и
повторного запуска сервера, а после обновления страницы сообщения снова появляются
в интерфейсе.

Кнопка `Удалить диалог` удаляет текущий диалог и его сохранённый контекст. База
добавлена в `.gitignore` и не отправляется в GitHub. При первом запуске старая
JSON-история автоматически переносится в SQLite. Режимы сравнения остаются
независимыми экспериментами и не добавляются в постоянную историю обычного чата.

Боковая панель показывает все сохранённые диалоги, их названия по первому запросу
и количество сообщений. Кнопка `+ Новый` начинает отдельный диалог, а выбор записи
из списка загружает её сообщения и продолжает именно этот контекст. Кнопка
`Удалить диалог` удаляет только открытую беседу.

## Сравнение трёх моделей

Флаг `Сравнить все 3 модели` параллельно отправляет один и тот же запрос в
DeepSeek V4 Pro, Gemma 3 4B и Qwen 3 8B. Для каждого ответа показываются полное
время запроса, входные, выходные и суммарные токены, а также расчётная стоимость
до списания бесплатных кредитов. После получения ответов DeepSeek отдельно
сравнивает их качество, скорость и ресурсоёмкость, выбирает победителя по каждому
критерию и формирует практический итог.

Стоимость является оценкой по опубликованным тарифам: для Hugging Face
используются цены маршрута `:cheapest`, для DeepSeek учитывается текущий период
`peak` или `off-peak` и объём кешированных входных токенов. Фактическое списание
может отличаться при изменении тарифов провайдера.

## Temperature

Флаг `Настроить temperature` включает явную передачу параметра в диапазоне от
`0` до `2`. Пока флаг выключен, параметр не отправляется и модель использует
настройку по умолчанию. При включении приложение переводит модель в non-thinking
режим, потому что DeepSeek игнорирует temperature в thinking mode. Выбранное
значение применяется к обычным запросам, диалогу и всем генерациям режима
сравнения.

Флаг `Сравнить 3 значения temperature` отправляет один и тот же запрос при
`temperature = 0`, `0.7` и `1.2`. Ответы показываются одновременно, после чего
отдельная генерация сравнивает их по точности, креативности и разнообразию. В
итоговом выводе указывается, для каких типов задач лучше подходит каждое значение.
Этот режим нельзя включить одновременно со сравнением четырёх промпт-подходов;
ручная настройка temperature на время сравнения отключается.

## Ограничение длины запроса

Флаг `Ограничить длину запроса` включает пользовательский предел от 1 до 12 000
символов. Рядом с полем запроса отображается живой счётчик. Если текст длиннее
выбранного значения, он не отправляется, а интерфейс показывает ошибку. Сервер
повторно проверяет ограничение во всех режимах, включая оба режима сравнения.
Когда флаг выключен, действует общий технический предел 12 000 символов.

## Сравнение четырёх подходов

Флаг `Сравнить 4 подхода к решению` запускает один и тот же запрос четырьмя
способами:

1. Прямой ответ без дополнительных инструкций.
2. Проверяемое пошаговое решение: цель, факты и ограничения, обоснованные шаги,
   проверка альтернатив и отдельный итог.
3. Сначала модель-помощник создаёт самодостаточный промпт с ролью, задачей,
   исходными данными, ограничениями, методом самопроверки и форматом ответа. Затем
   другая генерация решает задачу по созданному промпту.
4. Группа из аналитика, инженера и критика предлагает независимые решения.

После получения всех вариантов модель отдельно сравнивает их корректность,
полноту, понятность и надёжность, выбирает лучший подход и формирует итоговый
вывод. В режиме сравнения настройки формата и завершения временно отключаются,
чтобы прямой ответ не получал скрытых инструкций.

## Формат ответа

Модели передаётся строгая инструкция отвечать на русском языке тремя блоками:

1. `Краткий ответ:` — одно-два предложения.
2. `Основные пункты:` — нумерованный список из двух-пяти пунктов.
3. `Итог:` — одно заключительное предложение.

По умолчанию длина ответа не ограничивается. Галочка «Ограничить длину ответа»
включает поле «Максимум слов», где можно указать значение от 20 до 2000.
Ограничение применяется в любом режиме только при включённом флаге. Сервер
проверяет фактическую длину и обрезает превышение. Формат полностью указан в
веб-интерфейсе. Галочка «Использовать структурированный формат» включает шаблон;
если снять галочку, запрос отправляется без инструкции о структуре ответа.

## Диалог до готового результата

В интерфейсе доступны четыре режима завершения:

- `Обычный ответ` — без дополнительного условия;
- `Явная инструкция` — пользователь задаёт модели правило завершения;
- `Stop sequence` — ответ обрезается на указанном маркере, сам маркер скрывается;
- `Уточнять до готовности` — модель ведёт диалог до выполнения критерия.

Режим `Уточнять до готовности` превращает одиночный запрос в диалог. Пользователь
описывает желаемый результат и критерий готовности. Пока данных не хватает, модель
задаёт по одному уточняющему вопросу. Когда условие выполнено, она возвращает
итоговый результат, а интерфейс показывает статус `Данных достаточно — итог готов`.

Например, для запроса о рецепте модель может уточнить вид салата, ингредиенты и
количество порций, после чего завершить сбор информации и выдать рецепт. История
полностью передаётся модели с каждым следующим запросом; новый диалог можно начать
отдельной кнопкой.
